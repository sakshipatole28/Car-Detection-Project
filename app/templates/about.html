Problem statement

A city traffic team wants to count cars automatically, both in footage from fixed roadside cameras (grayscale, side-on) and in photos staff upload from phones, where cars appear from any angle. They can't use a GPU, and every result has to be explainable and checkable.

Task: given an image, return a bounding box for every car, whatever its viewing angle. The system must run on a CPU and be scored on public benchmarks: the UIUC Image Database for Car Detection with its official protocol, and the held-out test split of Stanford Cars.

Two models

The app serves two detectors, and you can switch between them on the Detect page.

  • Any angle · CNN (default): an SSDlite MobileNetV3 detector pretrained on COCO, then fine-tuned on a CPU with three kinds of training image:
    • Stanford Cars photos (12,949 training images, every angle);
    • 2×2 mosaics of those photos, so it also learns small and multiple cars;
    • synthetic grayscale street scenes built from the UIUC patches, some of them with no car at all.
    The pretrained model is measured before fine-tuning, so the gain is shown rather than assumed.
  • Side view · HOG: the classical baseline, which only recognises side views. It uses HOG features with calibrated logistic regression, a sliding window over 9 scales, and non-maximum suppression.

Doing it properly

  1. No leakage: data is split before augmentation, and cross-validation is grouped so an image and its flip always fall in the same fold. Every threshold is chosen on validation data, never on test data.
  2. No train/serve skew: HOG features are computed identically for training patches and for live sliding windows, and a unit test checks this. The CNN's training data is grayscale, so every input is converted to grayscale at inference too.
  3. Hard-negative mining (HOG): background windows the first model mistakes for cars become extra negatives.
  4. A faithful metric: a Python port of the official UIUC Java evaluator, checked in CI to give identical results for both models.

MLOps

  • DVC runs four pipeline stages (train, evaluate, train_cnn, evaluate_cnn), with every setting in params.yaml. It also versions the 930 MB Stanford archive outside git.
  • MLflow records parameters, loss curves, cross-validation, validation and test metrics, and plots, and registers both models.
  • FastAPI serves this web interface, a REST API (?model=cnn|hog) and the request history.
  • BentoML packages both models as a separate, containerised inference service.
  • GitHub Actions runs linting and tests, retrains HOG, re-evaluates the CNN, enforces quality gates, checks against the Java evaluator, smoke-tests Docker, then publishes the image to GHCR.

Limitations

  • Each Stanford training photo shows one large car. Crowded scenes with many small or heavily occluded cars are harder; the mosaics and synthetic scenes only partly cover them.
  • The CNN was fine-tuned for only a few hundred iterations on a laptop CPU. A GPU and more training time would improve it further.
  • The HOG baseline only recognises side views, by design.
